# AIWA — Autonomous Interplanetary Web Application

Reference implementation of the architecture described in the AIWA
whitepaper. This repo contains two interchangeable implementations of the
same ledger contract (event DAG H_d + materialized view A = G(H_d, θ)):

- **`public/js/core/event-dag.js`** — pure JS implementation, zero
  dependencies, zero build step. This is what runs today.
- **`rust-core/`** — Rust implementation, compiled to WASM, meant to
  replace the JS version for production (performance, and sandboxing for
  third-party modules — layer X of the paper).

`public/js/core/ledger-bridge.js` is the only entry point the rest of the
app should import. It loads WASM if present, otherwise falls back to the
JS implementation. No other app logic should depend on knowing which of
the two is running.

Both implementations are verified against each other, not just against
themselves — see "Cross-language id parity" below.

## Project roadmap

The paper specifies six contributions and a seven-layer reference
architecture (transport, identity, ledger, economics, modules, AI,
presentation), plus conservation as a function distinct from accrual
(§6.1 vs §6.2). This table is the actual project scope — not just the
ledger — and is kept current as work lands.

| Layer / function | Paper ref. | Status |
|---|---|---|
| **Ledger** — event DAG H_d | §8, §8.1 | ✅ Done, JS/Rust id parity verified |
| **Economics** — G(H_d, θ): cadence, reward, scarcity | §9–13 | 🔨 Phases 1–4 done (cadence, reward, scarcity, full composed G); Phases 5–7 remain (cross-impl parity, deliberate counterexample, wired into app) — see plan below |
| **Identity** — Lemma 1, strong/weak scheme selection | §11, §26 | 🔨 Lemma 1 verified structurally for the accrual case (see Phase 4, `g-integration.test.mjs`); the general strong/weak scheme-selection mechanism (§26) not yet built |
| **Conservation** — proof-carrying transfer, replay-resistant consumption guard | §6.1, §7 | ⏳ Not started — a distinct mechanism from accrual, not a byproduct of G |
| **Economic security** — Sybil / patient-capital cost model | §24 | ⏳ Not started, now has a real G to analyze against |
| **Transport** — pluggable, partition-tolerant | §25 | ⏳ Not started |
| **Modules** — sandboxed third-party extensibility, `ctx` contract, economic self-declaration | §27 | ⏳ Not started — §27.2 now has a real reward function to validate module registration against |
| **AI layer** — advisory/triage, structurally non-authoritative | §28 | ⏳ Not started, depends on modules existing to triage |
| **Presentation** — theme/layout independence from module logic | §27.3 | ⏳ Not started, depends on modules |
| **Deliberately-broken counterexamples** — regression harness proving the tests can actually fail | §20–22 | 🔨 Partial: `tests/lemma1.test.mjs` covers the weak-identity case; economics Phase 6 (wall-clock-instead-of-q) still open |

Current focus: **economics (G) Phases 5–7**, since Phases 1–4 (a real,
tested, composed G) unblock modules (§27.2) and the strong/weak identity
choice (§11, §26) — both listed above as now able to proceed against a
real reward function rather than a hypothetical one.

## Economics (G) — development plan

`A = G(H_d, θ)`, per §9–13.

- **Phase 0 — Contract.** `θ = {K, α, β, Δ, scarcityPolicy, budgetPerDomain}`.
  Event types: `genesis`, `cadence` (advances q_d), `accrual` (issuance,
  carries b and q_0). Materialized state:
  `{ domains: { [d]: { q_d, balance, issuanceTotal } }, globalIssuance }`.
- **Phase 1 — Cadence epochs (§10, Def. 10.1).** ✅ Done. Monotonic q_d,
  replay-protected (causal chaining to the domain's last accepted
  transition), bounded advancement (exact +1, no skipping). Implemented
  identically in `public/js/core/economics/cadence.js` and
  `rust-core/src/economics/cadence.rs`. 10 JS tests
  (`node --test tests/*.test.mjs`) + 8 Rust tests (`cargo test economics`
  in `rust-core/`), including: skipped epoch rejected, un-chained
  transition rejected, forked competing transition at the same epoch
  rejected, independent domains advance independently, order/interleaving
  independence (§9), and — in the JS integration test — a simulated
  post-partition merge of two independently-built domains reconciling to
  the same state regardless of merge order.
- **Phase 2 — Reward function.** ✅ Done. `r(b, q) = K · b^α · q^β`,
  implemented identically in `reward.js` / `reward.rs`, plus
  `elapsedEpochs()` deriving q from the cadence state built in Phase 1
  (q = current domain epoch − event's acceptance epoch q_0, never
  negative). Cross-checked against Appendix D.2's worked sub-expression
  (K=1, B=1000, t=1, α=0.5 → ≈31.6227766). 13 new tests (10 JS + 10 Rust,
  overlapping on shared cases), plus `tests/lemma1.test.mjs`: an
  *executable* version of Lemma 1 (§11) — constructs the exact
  counterexample the paper describes in prose (a weak identifier that
  omits q collides two events with different reward under
  cadence-sensitive β, and does not collide them — safely — when β=0).
- **Phase 3 — Scarcity policy (§13).** ✅ Done (v1 scope: unbounded control
  + §13.1 preallocated budget). `scarcity.js` / `scarcity.rs` implement
  `applyIssuanceAttempt()` (clamps to remaining per-domain budget, or
  unclamped if budget is null — the "Policy A" unbounded control case)
  and `simulateHourlyIssuance()`, a generic reproduction of Appendix
  H.4's simulation loop. Cross-checked directly against the paper's own
  worked numbers, not just internally consistent: Appendix D.1's
  unbounded case (I(1000h)=2000, I(10000h)=20000) and its preallocated-
  budget case (B_E=B_M=5000 → I saturates at 10000 and stays there
  through 100,000h) both reproduce exactly, in both languages
  independently. 28 tests total (28 JS across the whole suite + 30 Rust
  after this phase). Rate limits (§13.2) and expiring rights (§13.3) are
  deferred to v2, per the original plan.
- **Phase 4 — Full G.** ✅ Done. `g.js` / `g.rs` compose Phases 1–3 into
  one fold over a topologically-ordered event list: `cadence` events
  delegate to the cadence reducer; `accrual` events (`{domain, b, q0}`)
  derive q from the cadence state *as folded so far*, compute the
  requested reward, and hand it to the scarcity reducer — only the
  clamped, actually-issued amount reaches the domain's balance. No new
  identity check was needed to satisfy Lemma 1 (§11): because accrual
  payloads carry q0 and the DAG's id already hashes the full
  canonicalized payload (§8.1), economically distinct accrual events
  cannot collide — confirmed directly in
  `tests/g-integration.test.mjs`'s Lemma 1 integration case. 20 new tests
  (12 JS across `g.test.mjs` + `g-integration.test.mjs`, 6 Rust unit
  tests — full suite now 36 JS / 36 Rust).
- **Phase 5 — Cross-implementation parity.** ✅ Done. Extended the
  Phase 0 id-parity approach to the full composed G:
  `test-vectors/g-scenario.json` (ten events: two independent domains, a
  deliberate epoch-skip, a deliberate negative-b accrual), computed by
  `scripts/check-g-parity.mjs` and `rust-core/examples/check_g_parity.rs`,
  diffed (semantically, not textually — `40` vs `40.0` are equal)
  by `scripts/verify-g-parity.sh`, and pinned as a regression test in
  both languages (`tests/g-scenario.test.mjs`,
  `rust-core/tests/g_scenario.rs`). **Found a second real
  cross-implementation gap in the process**, the same way §8.1's
  encoding gap was found: JS and Rust materialize identical values (d1
  balance = 40), but only because both share the same canonical
  tie-breaking rule (id-sorted depth-first) for topological order.
  §9's "G is a deterministic function of the converged event set" is
  necessary but not sufficient for two implementations to *agree* —
  each can independently satisfy it while disagreeing with the other,
  if they pick different (both valid) tie-breaking rules for concurrent
  branches. Documented in the whitepaper as new §9.1 / §29.10 /
  Appendix H.7, mirroring §8.1's treatment.
- **Phase 6 — Deliberate counterexample.** ✅ Done. Built the exact
  broken variant the whitepaper's v1.1 revision note only argued against
  in prose: a G that derives q from an injected wall-clock reading
  instead of cadence state (`tests/counterexample-wallclock.test.mjs`,
  `rust-core/tests/counterexample_wallclock.rs` — deliberately kept out
  of `public/js/core/economics/` and `rust-core/src/economics/` so it
  can never be mistaken for usable code). Confirms two things per
  language: a control (the real G materializes the same event set
  identically regardless of when it's computed) and the counterexample
  itself (the broken variant materializes the *same* event set to a
  100x-different balance depending solely on an injected wall-clock
  value, 10 vs. 1000). Promotes the whitepaper's §10 wall-clock argument
  from asserted to executed — new Appendix H.8. 4 new tests (2 JS + 2
  Rust).
- **Phase 7 — Wire into the app.** Minimal display in `main.js`: balance
  per domain, epoch, cumulative issuance.

## Deploy to GitHub Pages

Everything lives in this GitHub repo; no separate hosting account needed.

One-time setup (repo settings, not a command):

1. GitHub repo → **Settings → Pages**
2. Under "Build and deployment", set **Source** to **GitHub Actions**

That's it. `.github/workflows/deploy-pages.yml` deploys `public/` on
every push to `main` (and can also be triggered manually from the
Actions tab). No build step — it's the same pure JS `public/` directory
described above, deployed as-is.

## Rust core: tests and build

The Rust logic lives in `rust-core/src/core.rs` as plain Rust (no
wasm-bindgen, no JsValue), specifically so it can be unit tested with a
normal, native `cargo test` — no `wasm32` target required for that.
`rust-core/src/dag.rs` is a thin wasm-bindgen wrapper around it that only
converts JsValue <-> serde_json::Value at the JS/Rust boundary; it has no
logic of its own and is intentionally left untested at the Rust level
(JsValue calls require a real JS/wasm host to run).

```bash
cd rust-core
cargo test          # 7 unit tests on the pure Rust core
```

### Build Rust → WASM

Building for `wasm32-unknown-unknown` requires the target's precompiled
std library, normally installed via `rustup target add
wasm32-unknown-unknown`. **This cannot be done from this sandboxed dev
environment**: `rustup`'s installer domain is not reachable from here, and
no prebuilt `wasm32` std package exists in the Ubuntu apt repositories.
`cargo check` / `cargo test` (native, x86_64) both pass, which validates
the logic, but the actual `.wasm` binary has to be produced either on a
machine with `rustup`, or by CI.

```bash
# on a machine with rustup:
rustup target add wasm32-unknown-unknown
cargo install wasm-pack
cd rust-core
wasm-pack build --target web --out-dir ../public/js/wasm --out-name aiwa_core
```

This generates `public/js/wasm/aiwa_core.js` (+ the `.wasm` file), which
`ledger-bridge.js` will pick up automatically on next reload — no other
file needs to change.

The `wasm-build` job in `.github/workflows/ci.yml` does exactly this on
every push and uploads the result as a downloadable build artifact, so a
real WASM build is available without needing a local Rust setup at all.

## Cross-language id parity

The paper's replicated-state / economic-meaning separation (§3.1) only
holds if both implementations of H_d agree on identity. `computeId()` in
JS and `Event::compute_id()` in Rust must produce byte-identical SHA-256
digests for the same logical (parents, payload) — including for nested
objects, regardless of key insertion order.

This was **not true by default**: `JSON.stringify` in JS preserves key
insertion order at every nesting level, while `serde_json::Value` in Rust
sorts keys alphabetically by default. The JS side now recursively
canonicalizes (sorts) object keys before hashing, matching Rust's
behavior — see `canonicalize()` in `event-dag.js`.

This is checked automatically, not just asserted:

```bash
./scripts/verify-parity.sh
```

Runs both implementations over the shared fixture in
`test-vectors/id-parity.json` (flat payloads, nested payloads, arrays,
unsorted parents, different key orders for the same logical object) and
diffs the output. Currently: 6/6 vectors match. This also runs in CI on
every push (`id-parity` job).

## Whitepaper

`docs/AIWA_whitepaper_v1_2_revised.md` is kept in sync with this
implementation, not treated as a separate, static document. When the
implementation surfaces a real finding — a bug, a gap the paper's model
didn't cover, a divergence between what's specified and what's actually
required for two implementations to interoperate — it gets a precise,
appropriately-scoped addition in the paper itself, in the same place the
paper already states every other limitation (not a changelog bullet
divorced from the argument it affects).

Current implementation-driven additions: **§8.1** and **§29.9** (canonical
encoding across heterogeneous implementations), with before/after
evidence in **Appendix H.5**; **Appendix H.6** (the reward function
and §13.1 scarcity policy, independently reproduced in JS and Rust,
cross-checked exactly against Appendix D.1/D.2/H.4's own numbers), with
**H.6.1** documenting `tests/lemma1.test.mjs` as a minimal, deliberately
non-randomized companion to §22's existing randomized Lemma 1 experiment
— not a replacement for it; and **§9.1** / **§29.10** (canonical
materialization order is part of the identity/consensus contract, same
argument as §8.1 but for the function that orders events for folding,
not the one that encodes them), with evidence in **Appendix H.7**; and
**Appendix H.8**, which promotes §10's wall-clock-vs-cadence argument
(previously asserted only in prose) to an executed deliberate
counterexample, in the spirit of §20–22.

**Fixed**: the paper's body text previously cited "Appendix J.1–J.3" for
the four experiments in §20–22, while the document only ever defined an
"Appendix H — Full Experimental Source Code." All such citations now
