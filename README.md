# AIWA — Autonomous Interplanetary Web Application

Reference implementation of the architecture described in the AIWA
whitepaper. This repo contains two interchangeable implementations of the
same ledger contract (event DAG H_d + materialized view A = G(H_d, θ)):

- **`public/js/core/event-dag.js`** — pure JS implementation, zero
  dependencies, zero build step. This is what runs today.
- **`rust-core/`** — Rust implementation, compiled to WASM, meant to
  replace the JS version for production (performance, and sandboxing for
  third-party modules — layer X of the paper).

`public/js/core/ledger-bridge.js` is the only entry point the rest of the
app should import. It loads WASM if present, otherwise falls back to the
JS implementation. No other app logic should depend on knowing which of
the two is running.

Both implementations are verified against each other, not just against
themselves — see "Cross-language id parity" below.

## Project roadmap

The paper specifies six contributions and a seven-layer reference
architecture (transport, identity, ledger, economics, modules, AI,
presentation), plus conservation as a function distinct from accrual
(§6.1 vs §6.2). This table is the actual project scope — not just the
ledger — and is kept current as work lands.

| Layer / function | Paper ref. | Status |
|---|---|---|
| **Ledger** — event DAG H_d | §8, §8.1 | ✅ Done, JS/Rust id parity verified |
| **Economics** — G(H_d, θ): cadence, reward, scarcity | §9–13 | ✅ Done — all 7 phases (cadence, reward, scarcity, composed G, cross-impl parity, deliberate counterexample, wired into the app); JS only so far, WASM-side not yet wired (see Status) |
| **Identity** — Lemma 1, strong/weak scheme selection, c_id | §11, §26, §24 | 🔨 Lemma 1 verified structurally (Phase 4, `g-integration.test.mjs`); a concrete c_id mechanism (SOL burn, §24.6) built and tested — see "Identity cost" below; strong/weak scheme *selection* (§26) and wiring c_id into accrual (§10) not yet done |
| **Conservation** — proof-carrying transfer, replay-resistant consumption guard | §6.1, §7 | ✅ Done — all 5 phases (state machine, consume guard, transmutation, deliberate crash-safety counterexample, cross-language parity); not yet wired to economics (claims aren't created from accrual balances yet) |
| **Economic security** — Sybil / patient-capital cost model | §24 | ⏳ Not started, now has a real G to analyze against |
| **Transport** — pluggable, partition-tolerant | §25 | ⏳ Not started |
| **Modules** — sandboxed third-party extensibility, `ctx` contract, economic self-declaration | §27 | 🔨 Open registration + content integrity + real iframe sandbox mechanism built and tested (JS/Rust logic); not wired into a UI yet — see "Modules" below |
| **AI layer** — advisory/triage, structurally non-authoritative | §28 | ⏳ Not started, depends on modules existing to triage |
| **Presentation** — theme/layout independence from module logic | §27.3 | ⏳ Not started, depends on modules |
| **Deliberately-broken counterexamples** — regression harness proving the tests can actually fail | §20–22 | 🔨 `tests/lemma1.test.mjs` (weak-identity case) and `tests/counterexample-wallclock.test.mjs` (§9/§10 wall-clock case) done; not yet generalized beyond economics |

Current focus: economics (G) is complete (all 7 phases). Next up:
either wiring the WASM build into `ledger-bridge.js` and the economics
reducers (independent of everything else), or moving to a layer that G
now unblocks — identity's strong/weak scheme selection (§11, §26) or
modules (§27.2), both of which need a real reward function to validate
against, which now exists.

## Economics (G) — development plan

`A = G(H_d, θ)`, per §9–13.

- **Phase 0 — Contract.** `θ = {K, α, β, Δ, scarcityPolicy, budgetPerDomain}`.
  Event types: `genesis`, `cadence` (advances q_d), `accrual` (issuance,
  carries b and q_0). Materialized state:
  `{ domains: { [d]: { q_d, balance, issuanceTotal } }, globalIssuance }`.
- **Phase 1 — Cadence epochs (§10, Def. 10.1).** ✅ Done. Monotonic q_d,
  replay-protected (causal chaining to the domain's last accepted
  transition), bounded advancement (exact +1, no skipping). Implemented
  identically in `public/js/core/economics/cadence.js` and
  `rust-core/src/economics/cadence.rs`. 10 JS tests
  (`node --test tests/*.test.mjs`) + 8 Rust tests (`cargo test economics`
  in `rust-core/`), including: skipped epoch rejected, un-chained
  transition rejected, forked competing transition at the same epoch
  rejected, independent domains advance independently, order/interleaving
  independence (§9), and — in the JS integration test — a simulated
  post-partition merge of two independently-built domains reconciling to
  the same state regardless of merge order.
- **Phase 2 — Reward function.** ✅ Done (superseded by the Proof-of-Will
  revision, see the changelog entry below — kept here for phase-history
  continuity). `r(b, q, q_total, T) = (b·q^α)/[ln(q_total^(β(1−T))+C)]^γ`,
  implemented identically in `reward.js` / `reward.rs`, plus
  `elapsedEpochs()`/`domainAge()` deriving q and q_total from the
  cadence state built in Phase 1 (q = current domain epoch − event's
  acceptance epoch q_0, never negative). Cross-checked against the real
  reference implementation's own constants (α=1.1, β=2.2, γ=3,
  C=33³), not against Appendix D.2's worked example, which reflects the
  earlier power-law form
  (K=1, B=1000, t=1, α=0.5 → ≈31.6227766). 13 new tests (10 JS + 10 Rust,
  overlapping on shared cases), plus `tests/lemma1.test.mjs`: an
  *executable* version of Lemma 1 (§11) — constructs the exact
  counterexample the paper describes in prose (a weak identifier that
  omits q collides two events with different reward under
  cadence-sensitive β, and does not collide them — safely — when β=0).
- **Phase 3 — Scarcity policy (§13).** ✅ Done (v1 scope: unbounded control
  + §13.1 preallocated budget). `scarcity.js` / `scarcity.rs` implement
  `applyIssuanceAttempt()` (clamps to remaining per-domain budget, or
  unclamped if budget is null — the "Policy A" unbounded control case)
  and `simulateHourlyIssuance()`, a generic reproduction of Appendix
  H.4's simulation loop. Cross-checked directly against the paper's own
  worked numbers, not just internally consistent: Appendix D.1's
  unbounded case (I(1000h)=2000, I(10000h)=20000) and its preallocated-
  budget case (B_E=B_M=5000 → I saturates at 10000 and stays there
  through 100,000h) both reproduce exactly, in both languages
  independently. 28 tests total (28 JS across the whole suite + 30 Rust
  after this phase). Rate limits (§13.2) and expiring rights (§13.3) are
  deferred to v2, per the original plan.
- **Phase 4 — Full G.** ✅ Done. `g.js` / `g.rs` compose Phases 1–3 into
  one fold over a topologically-ordered event list: `cadence` events
  delegate to the cadence reducer; `accrual` events (`{domain, b, q0}`)
  derive q from the cadence state *as folded so far*, compute the
  requested reward, and hand it to the scarcity reducer — only the
  clamped, actually-issued amount reaches the domain's balance. No new
  identity check was needed to satisfy Lemma 1 (§11): because accrual
  payloads carry q0 and the DAG's id already hashes the full
  canonicalized payload (§8.1), economically distinct accrual events
  cannot collide — confirmed directly in
  `tests/g-integration.test.mjs`'s Lemma 1 integration case. 20 new tests
  (12 JS across `g.test.mjs` + `g-integration.test.mjs`, 6 Rust unit
  tests — full suite now 36 JS / 36 Rust).
- **Phase 5 — Cross-implementation parity.** ✅ Done. Extended the
  Phase 0 id-parity approach to the full composed G:
  `test-vectors/g-scenario.json` (ten events: two independent domains, a
  deliberate epoch-skip, a deliberate negative-b accrual), computed by
  `scripts/check-g-parity.mjs` and `rust-core/examples/check_g_parity.rs`,
  diffed (semantically, not textually — `40` vs `40.0` are equal)
  by `scripts/verify-g-parity.sh`, and pinned as a regression test in
  both languages (`tests/g-scenario.test.mjs`,
  `rust-core/tests/g_scenario.rs`). **Found a second real
  cross-implementation gap in the process**, the same way §8.1's
  encoding gap was found: JS and Rust materialize identical values (d1
  balance = 40), but only because both share the same canonical
  tie-breaking rule (id-sorted depth-first) for topological order.
  §9's "G is a deterministic function of the converged event set" is
  necessary but not sufficient for two implementations to *agree* —
  each can independently satisfy it while disagreeing with the other,
  if they pick different (both valid) tie-breaking rules for concurrent
  branches. Documented in the whitepaper as new §9.1 / §29.10 /
  Appendix H.7, mirroring §8.1's treatment.
- **Phase 6 — Deliberate counterexample.** ✅ Done. Built the exact
  broken variant the whitepaper's v1.1 revision note only argued against
  in prose: a G that derives q from an injected wall-clock reading
  instead of cadence state (`tests/counterexample-wallclock.test.mjs`,
  `rust-core/tests/counterexample_wallclock.rs` — deliberately kept out
  of `public/js/core/economics/` and `rust-core/src/economics/` so it
  can never be mistaken for usable code). Confirms two things per
  language: a control (the real G materializes the same event set
  identically regardless of when it's computed) and the counterexample
  itself (the broken variant materializes the *same* event set to a
  100x-different balance depending solely on an injected wall-clock
  value, 10 vs. 1000). Promotes the whitepaper's §10 wall-clock argument
  from asserted to executed — new Appendix H.8. 4 new tests (2 JS + 2
  Rust).
- **Phase 7 — Wire into the app.** ✅ Done, then rebuilt around the
  paper's actual central claim rather than a generic balance table.
  `main.js`/`index.html` now simulate two independent domains, Earth and
  Mars, each with its own `EventDag` instance. **Partitioned is the
  default state**, not an error state — both domains keep accruing
  locally with zero coordination, matching §9's premise directly rather
  than just displaying numbers. `Commit` records a resource claim at the
  current cadence epoch (client-side, no ledger event yet); `Claim
  reward` posts it — reward requires elapsed cadence epochs between the
  two, never instant (§10), which is itself demonstrable in the UI, not
  just asserted. `Reconcile` merges both DAGs (set union, both
  directions) and — this is the important part — the app then
  recomputes both domains' balances from *both* replicas' now-identical
  local event sets and logs whether they agree, checking §9's
  determinism claim live rather than assuming it. `tests/main-demo.test.mjs`
  pins this scenario exactly (Earth=20, Mars=10, converges to
  `{earth:20, mars:10}` on both sides, 7 events either way). 4 new/rewritten tests.

  **A real deployed-page bug found and fixed in the process**:
  `public/js/core/wasm-ledger-adapter.js` (added when WASM was wired,
  see above) never actually made it into the GitHub repo — a 404 on a
  static `import` in `ledger-bridge.js`, which breaks the whole module
  graph silently (no console-visible exception reaches `main()`'s own
  `.catch()`, since the module never starts executing). The page was
  stuck on "Initializing…" indefinitely with an empty table. Confirmed
  directly against the live repo (`raw.githubusercontent.com`, not
  guessed) before concluding what was missing.

## Conservation (§6.1, §7)

Structurally distinct from economics (G): conservation moves or converts
an *existing* claim (`Deactivate → Prove → Verify → Consume → Activate`);
it never creates value from nothing consumed, which is exactly what
accrual (G) does instead. The two are separate modules
(`public/js/core/conservation/`, `rust-core/src/conservation/`) and are
not yet wired together — a claim isn't automatically created from an
accrual event's issued balance; that integration is future work.

- **Phase 1–2 — Claim state machine + proof/consume guard.** ✅ Done.
  `conservation.js` / `mod.rs` implement all five pipeline steps as
  individually-callable functions (not just a black-box orchestrator),
  so tests can interleave or repeat steps directly. The load-bearing
  invariant, `count(Consume(p)) ≤ 1` (§7), is a direct port of the
  whitepaper's own reference pseudocode.
- **Phase 3 — Transmutation.** ✅ Done. A transfer and a transmutation go
  through the identical pipeline; a transfer is simply a transmutation
  whose derivation function is `identityDerivation`. Tested with the
  concrete "burn X, mint Y at a fixed rate" case.
- **Phase 4 — Deliberate counterexample (crash-safety).** ✅ Done. Built
  the exact "crash window" §7 warns about in prose: split the real,
  atomic `consume()` into two separate steps (check, then commit),
  matching what a persisted-but-non-atomically-checked consumption
  record would look like in production. Control: real `consume()`
  correctly rejects a second attempt; only one destination claim ever
  exists. Counterexample: the split version lets two independent
  branches both pass the check before either commits, and both
  successfully activate — two destination claims minted from a single
  proof, the literal double-spend. Deliberately kept out of
  `conservation/` in both languages
  (`tests/counterexample-nonatomic-consume.test.mjs`,
  `rust-core/tests/counterexample_nonatomic_consume.rs`). 4 new tests
  (2 JS + 2 Rust).
- **Phase 5 — Cross-language parity.** ✅ Done. Extended the same
  fixture/script/pinned-regression-test pattern used for economics (G):
  `test-vectors/conservation-scenario.json` (a same-kind transfer and a
  transmutation), `scripts/check-conservation-parity.mjs` /
  `rust-core/examples/check_conservation_parity.rs`,
  `scripts/verify-conservation-parity.sh`, and pinned regression tests
  in both languages. JS and Rust agree exactly. 2 new tests (1 JS + 1
  Rust).

**Citation fix landed**: §7's "Appendix B.7" mis-citation (found while
implementing Phases 1–3, see above) is now corrected in the whitepaper —
Appendix B.7 is consistently, correctly used everywhere else in the
document for the *merge* replay guard (a different mechanism); §7 now
points to Appendix B's general reference pseudocode and to the new
**Appendix H.9**, which documents both the Phase 4 counterexample and
the Phase 5 parity check.

25 tests total for Conservation (13 JS + 12 Rust; 62 JS / 51 Rust across
the whole project).

## Identity cost — c_id via a one-time SOL burn (§24, §26)

Answers a question the whitepaper deliberately leaves open (§1, §29):
"physical truth of committed claims... remain open." `b` in the reward
function (§10) is only meaningful if it costs something real to claim —
otherwise Sybil resistance (§24) has nothing to bite on. This module is
one concrete answer, not the only possible one, following §24.6's
"local proof-of-work registration" family but using a real-world sunk
cost (a SOL burn) instead of computational work.

**Why burn, not bond/stake** — discussed with the user before building
this, worth recording here rather than only in chat history. §24.6.i
(bonded-capital staking) depends on slashing being enforced after
misbehavior is detected; the paper states plainly that under an
arbitrarily long partition, "the usable floor during a partition of
length T shrinks as T grows, exactly the opposite of what a designer
might hope." A burn has no such dependency — the cost is sunk the
instant it's paid, with nothing left to enforce later. For a protocol
whose entire premise is that "later" may never arrive during the period
that matters, that property is worth more than the capital efficiency a
bond would otherwise offer.

**Mechanism**: before entering partition (i.e. while still connected),
a domain burns real SOL on Solana mainnet — sent to the network's
well-known, real, documented incinerator address
(`1nc1nerator11111111111111111111111111111111`, verified against
multiple independent sources, not invented for this project). The
resulting transaction signature, once finalized, becomes that domain's
proof of `c_id`. Once partition begins, nothing further needs to happen
on Solana — this matches the "sunk, not enforced" property above exactly.

**Split into three files, not two, now**: `identity-cost.js` (pure
verification + replay-guarded registration logic, fully unit tested —
10 JS + 9 Rust tests), `solana-wallet.js` (real keypair generation,
password encryption via Web Crypto, and burn-transaction
construction/signing — tested against the **real** `@solana/web3.js`
library, not a hand-rolled fake, installed as a test-only devDependency;
see `package.json` — 6 tests, including a real Ed25519 signature that
gets verified by round-tripping through `Transaction.from()`), and
`solana-rpc.js` (the actual network call to Solana mainnet, which
**still cannot be exercised or verified from this development sandbox**
— outbound access here doesn't reach Solana RPC endpoints, the same
limitation already documented for why the real `wasm32` build can't be
produced locally either). Only the final broadcast-and-confirm step
(`broadcastBurnTransaction()`) is unverified now; everything before it —
key generation, encryption, transaction construction, signing,
serialization — is real, tested code, not a placeholder.

**Is Solana a permanent commitment? No — the boundary was drawn for
exactly this reason.** `identity-cost.js` operates only on a
chain-agnostic `NormalizedBurnTx` shape; nothing in its verification or
registration logic mentions Solana. `solana-wallet.js` and
`solana-rpc.js` are the only Solana-specific files, mirroring the same
pluggable-adapter shape already used for `WasmLedgerAdapter`. Adding a
second chain later means writing a new `xxx-wallet.js` / `xxx-rpc.js`
pair that produces the same `NormalizedBurnTx` shape — no change to
`identity-cost.js` at all.

now have a per-domain identity block: create/unlock a real wallet

in an actual browser, on devnet, with a wallet funded from a faucet.

## Modules (§27)

**Real gap found and fixed after deployment, not before**: everything
below was built as a standalone `ModuleRegistryState` object with no
propagation mechanism — the user asked "le registre traverse les
domaines, grâce au miroir?" and the honest answer was no. The JS/Rust
mirror is portability, not replication; nothing moved a registration
from one domain to another. Under connectivity this is invisible; under
partition — this project's actual premise — Mars would never learn what
Earth registered, or vice versa, ever. Fixed in
`module-registry-reducer.js` / `module_registry_reducer.rs`: module
registration/update/audit are now DAG event types
(`module-register`/`module-update`/`module-audit`), and the registry is
`registry(H_d)` — a materialized view exactly like `g.js`, propagated
for free by `EventDag#merge()`, folded deterministically by
`topoOrder()` (§9). 4 JS + 3 Rust tests directly prove the property that
was missing: a module registered on Earth is genuinely absent from
Mars's own materialized registry before reconciliation, and both
converge to the identical registry after merging, regardless of merge
order.

Built after reviewing real prior code the user shared for inspiration (a
working module/theme registry from another of their projects) and
critiquing it directly: that reference loaded remote module code via
`<script src="blob:...">`, same-origin, full access to `window`,
`localStorage`, and `fetch` — the documented sandbox rules ("a module
must not intercept `window.fetch`") existed only as convention, nothing
enforced them. This module follows the user's explicit governance
philosophy — publishing stays maximally open, no gatekeeping, "I audit,
I judge, unaudited-by-default is red-listed" (audit itself: AI-driven,
future work, not built here) — while fixing two specific technical gaps
that philosophy depends on but doesn't by itself guarantee, especially
under partition where no community judgment can be freshly fetched:

- **`module-hash.js` + `module-registry.js`** (pure, fully tested: 4 + 14
  JS, 4 + 11 Rust). Registration is open — no author allow-list, the
  only rejections are mechanical (duplicate id) or, for an
  accrual-issuing module only, an internally-inconsistent economic
  declaration per §27.2/§24.1 (this project's own real `reward.js`
  math, not a placeholder check). Every registration binds an id to a
  content hash, not a mutable URL — a judgment ("audited, passed",
  "red-listed") stays attached to the exact bytes it was made about;
  `updateModuleCode()` resets audit status to `unaudited` on every code
  change, so a stale verdict can never silently apply to different code.
- **`module-sandbox.js`** (real mechanism, untestable here — no browser
  DOM under `node --test`, same category as `solana-rpc.js`). Module
  code runs inside a real `<iframe sandbox="allow-scripts">` —
  deliberately *without* `allow-same-origin`, which is what makes the
  sandbox's isolation a property of where the code executes rather than
  a rule the code is asked to follow. A minimal `ctx`
  (`storage.get/set`, `toast`, `commit`, `claim`) is bridged over
  `postMessage`, invisible to the module author — publishing stays
  exactly as frictionless as before; only execution is now actually
  contained. A module whose fetched code doesn't match its registered
  hash is refused mounting outright.

This closes a specific, previously "unconfirmed" claim in the
whitepaper's own security property registry (R19, Appendix E) — see
§27.4 and Appendix H.11. It does not establish that the sandbox is
unbreakable, or that it has survived adversarial escape attempts —
neither claim is made.

**The submission pipeline itself** — added after the user shared their
real prior CI implementation (`validate.js`/`merge.js`: code stays in
the author's own fork, a PR carries only a signed event, a GitHub Action
re-fetches and hash-checks the real bytes before merging) and asked
"où est le code soumis?" A question that exposed a real gap:
`registerModule()` alone trusted a caller-supplied `codeHash` on faith —
nothing actually fetched the code and checked it before registering. The
prior implementation shared for reference gets this partly right and has
one precise, fixable gap of its own, found by reading `merge.js` (line
83–98): the hash verified at merge time is never written into `files.json`,
so nothing exists for a later fetch, months or years on, to be re-checked
against. Both are closed here:

- **`module-submission.js`** (pure, tested with **real** Ed25519
  signing via `@noble/curves` — 9 tests): builds and verifies a signed
  submission event (moduleId, codeHash, codeUrl, nonce, timestamp,
  signature), checks it against the actual fetched code (not the
  caller's claim), replay-guards nonces, and only then registers or
  updates the module — closing exactly the gap above, since
  `module-registry.js`'s `codeHash` is stored permanently in the entry,
  not discarded after a one-time check. Signing is for attribution and
  integrity only — deliberately **no economic gate**, unlike the shared
  reference's rising-score requirement for new files, per the user's
  explicit instruction to keep publishing maximally open.
- **`module-fetch.js`** (real network call — untestable here, same
  category as `solana-rpc.js`): the one thin function that actually
  fetches `codeUrl` and feeds it into the pure pipeline above.
- **Rust mirror, `module_submission.rs`**, tested against **real**
  `ed25519-dalek` signing (8 tests) — not a stub. One noted, unverified
  assumption rather than a silent gap: the JS and Rust canonical
  message-construction functions are written to produce byte-identical
  output by careful field-order matching, but — unlike `id-parity.json`
  for ledger events — there is not yet an automated cross-language
  parity script proving a JS-signed submission verifies under the Rust
  verifier and vice versa. Recorded as open work, not assumed solved.

**Not yet done**: wiring modules into the app UI, and the optional ψ
growth-condition symbolic check the paper's own reference pseudocode
allows (`validateEconomicConfig`, §24.3) but does not require — recorded
as a deliberate scope decision (Appendix H.11), not an oversight.

## Rust core: tests and build

The Rust logic lives in `rust-core/src/core.rs` as plain Rust (no
wasm-bindgen, no JsValue), specifically so it can be unit tested with a
normal, native `cargo test` — no `wasm32` target required for that.
`rust-core/src/dag.rs` is a thin wasm-bindgen wrapper around it that only
converts JsValue <-> serde_json::Value at the JS/Rust boundary; it has no
logic of its own and is intentionally left untested at the Rust level
(JsValue calls require a real JS/wasm host to run).

```bash
cd rust-core
cargo test          # 7 unit tests on the pure Rust core
```

### Build Rust → WASM

Building for `wasm32-unknown-unknown` requires the target's precompiled
std library, normally installed via `rustup target add
wasm32-unknown-unknown`. **This cannot be done from this sandboxed dev
environment**: `rustup`'s installer domain is not reachable from here, and
no prebuilt `wasm32` std package exists in the Ubuntu apt repositories.
`cargo check` / `cargo test` (native, x86_64) both pass, which validates
the logic, but the actual `.wasm` binary has to be produced either on a
machine with `rustup`, or by CI.

```bash
# on a machine with rustup:
rustup target add wasm32-unknown-unknown
cargo install wasm-pack
cd rust-core
wasm-pack build --target web --out-dir ../public/js/wasm --out-name aiwa_core
```

This generates `public/js/wasm/aiwa_core.js` (+ the `.wasm` file), which
`ledger-bridge.js` will pick up automatically on next reload — no other
file needs to change.

The `wasm-build` job in `.github/workflows/ci.yml` does exactly this on
every push and uploads the result as a downloadable build artifact, so a
real WASM build is available without needing a local Rust setup at all.

**What "wired" means right now, precisely**: `ledger-bridge.js` will load
that artifact and hand it to `WasmLedgerAdapter`
(`public/js/core/wasm-ledger-adapter.js`), which translates the raw Rust
wasm-bindgen surface (`topoOrderJson()` returning a string, `size()` as a
method) to the exact interface the pure JS `EventDag` already provides
(`topoOrder()` returning an array, `size` as a getter) — main.js and the
economics reducers call the same methods either way and cannot tell
which backend is active. This translation logic is tested end to end
(`tests/ledger-bridge.test.mjs`, `tests/wasm-ledger-adapter.test.mjs`)
against a fake module built to the real Rust surface's exact shape, which
is how two real shape mismatches were found and fixed before ever
touching a browser. **Update**: the real compiled `.wasm` binary is now
committed automatically by CI (`ci.yml`'s `wasm-build` job, after fixing
three real, distinct CI failures found only by reading actual job
output rather than guessing — a lost executable bit, a stale
`.gitignore` rule, and a `.gitignore` `wasm-pack` itself regenerates
inside its own output directory on every build) and has been confirmed
to load without error in a real deployed browser session — the specific
gap this paragraph used to describe as open is closed, not merely
believed closed. What remains genuinely unverified: that the loaded WASM
module's *computed results* agree with the JS backend under real
browser conditions beyond "it loads" — the shape-parity tests above give
strong reason to expect this, but no test has yet compared live WASM-backed
and JS-backed outputs side by side in an actual browser session.

## Cross-language id parity

The paper's replicated-state / economic-meaning separation (§3.1) only
holds if both implementations of H_d agree on identity. `computeId()` in
JS and `Event::compute_id()` in Rust must produce byte-identical SHA-256
digests for the same logical (parents, payload) — including for nested
objects, regardless of key insertion order.

This was **not true by default**: `JSON.stringify` in JS preserves key
insertion order at every nesting level, while `serde_json::Value` in Rust
sorts keys alphabetically by default. The JS side now recursively
canonicalizes (sorts) object keys before hashing, matching Rust's
behavior — see `canonicalize()` in `event-dag.js`.

This is checked automatically, not just asserted:

```bash
./scripts/verify-parity.sh
```

Runs both implementations over the shared fixture in
`test-vectors/id-parity.json` (flat payloads, nested payloads, arrays,
unsorted parents, different key orders for the same logical object) and
diffs the output. Currently: 6/6 vectors match. This also runs in CI on
every push (`id-parity` job).
